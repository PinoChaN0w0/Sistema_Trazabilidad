Sistema Alumnos · Documentación y trazabilidad

Sobre una API en Flask, su pipeline de Jenkins genera la documentación con Doxygen, exige que esté completa, la versiona en Git, despliega la app en un entorno de prueba y deja cada versión trazable hasta su commit.

Build→Test→Generate Documentation→Version Control→Deploy
Tiempo ≈ 2 h 30 min + entregaModalidad parejasHerramientas Docker · Jenkins · Git · pipenv · Doxygen

Cómo usar esta guía

  • Marquen Hecho en cada paso: el avance queda guardado en este navegador y el botón Seguir los lleva al siguiente paso pendiente.
  • Cada paso termina con un recuadro verde de Checkpoint (cómo saber que va bien) y, a veces, con uno punteado de Evidencia (captura que deben guardar para la entrega).
  • En pareja: una persona escribe y la otra lee y revisa; cambien de rol en cada Checkpoint. Ambos deben aparecer en el historial de Git.
  • Ningún secreto (tokens, contraseñas) en el repositorio ni en las capturas.

Esta es la guía 2 de 2. Si ya hicieron la guía de dependencias, marquen los Pasos 0 a 3 como hechos y sigan en B1.

Preparación

Paso 0 · 10 min

Preparen el equipo

Necesitan Docker con Compose, Git, una cuenta de GitHub (gratuita; la pareja usa un solo repositorio y agrega a su compañero/a como colaborador/a) y un editor como Visual Studio Code. Unos 2 GB libres e Internet.

Terminal
docker --version
docker compose version
docker run --rm hello-world
git --version

Configuren su identidad en Git (una vez por equipo):

Terminal
git config --global user.name "Tu Nombre"
git config --global user.email "tu_correo@ejemplo.cl"

Descompriman sistema_alumnos.zip en una ruta sin espacios ni tildes (por ejemplo C:\trabajo\). Dentro hay dos carpetas que usarán: jenkins/ (el laboratorio Docker) y proyecto/ (el código que subirán a GitHub).

Checkpoint

docker run --rm hello-world muestra «Hello from Docker!» y git --version responde una versión.

Paso 1 · 20 min

Levanten el laboratorio (Jenkins + taller)

Jenkins corre dentro de Docker. Junto a él se crea un segundo contenedor, taller, con Python, pipenv, pytest y Doxygen: así no instalan nada más en su equipo.

Terminal · carpeta jenkins/
cd sistema_alumnos/jenkins
docker compose up -d --build
docker compose ps

La primera vez tarda 3 a 5 minutos (mientras esperan, hagan el Paso 3.1). Deben ver dos contenedores Up: jenkins-alumnos y taller-alumnos.

Configuración inicial de Jenkins

Obtengan la contraseña de desbloqueo:

Terminal · carpeta jenkins/
docker compose exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
  1. Abran http://localhost:8080 y péguenla en Unlock Jenkins.
  2. Elijan Install suggested plugins (tarda unos minutos).
  3. Creen su usuario administrador (anoten la clave: no hay recuperación fácil).
  4. Dejen la URL como http://localhost:8080/ y pulsen Start using Jenkins.
Evidencia E1

Captura de docker compose ps y del panel de Jenkins ya configurado.

Checkpoint

Ven el Dashboard en http://localhost:8080 y docker compose ps muestra los dos contenedores.

Paso 2 · 10 min

Creen el Pipfile con pipenv

El pipeline instala con pipenv install --deploy y por eso necesita el Pipfile.lock (versiones exactas y hashes de lo que se instala). Ejecuten desde jenkins/:

Terminal · carpeta jenkins/
docker compose exec taller pipenv install -r requirements.txt
docker compose exec taller pipenv install --dev pytest
docker compose exec taller pipenv run pytest
Checkpoint

En proyecto/ aparecieron Pipfile y Pipfile.lock, y pytest informa 9 passed (los warnings son normales).

Paso 3 · 25 min

Repositorio en GitHub y pipeline base en Jenkins

3.1 Creen el repositorio

En GitHub: New repository → nombre sistema-alumnos → Public (así Jenkins lo clona sin credenciales) → no marquen README, .gitignore ni licencia → Create repository.

3.2 Suban el proyecto

Terminal · carpeta proyecto/
cd ../proyecto
git init -b main
git add .
git status
git commit -m "Proyecto inicial: Sistema Alumnos"
git remote add origin https://github.com/TU_USUARIO/sistema-alumnos.git
git push -u origin main

Antes del commit, git status debe mostrar Pipfile y Pipfile.lock, y no .venv/ ni reports/. GitHub ya no acepta la contraseña de la cuenta: el navegador les pedirá iniciar sesión.

3.3 Creen el job de Jenkins

  1. Dashboard → New Item → nombre sistema-alumnos → tipo Pipeline → OK.
  2. En la sección Pipeline: Definition = Pipeline script from SCM · SCM = Git · Repository URL = la URL de su repositorio (termina en .git) · Credentials = - none - · Branch Specifier = */main · Script Path = Jenkinsfile.
  3. Save y luego Build Now. Abran el build #1 → Console Output y lean el log de abajo hacia arriba.

Abran proyecto/Jenkinsfile: solo tiene las etapas Build y Test y varios comentarios >>> [ETIQUETA], que son los lugares donde pegarán etapas más adelante. Los que empiezan con [A-…] pertenecen a la otra guía: déjenlos como están.

Evidencia E2

Captura de la configuración del job (sección Pipeline) y del build #1 exitoso (Build y Test en verde).

Checkpoint

El build #1 termina en SUCCESS y el log muestra 9 passed.

Documentación y trazabilidad

Regla de la Parte B. Desde B4 Jenkins también hace commits en su repositorio. Antes de editar, siempre git pull; si no, su git push será rechazado.
Terminal · carpeta proyecto/
git pull
B1 · 10 min

Configuren Doxygen

Doxygen genera documentación (HTML) a partir de los comentarios del código. Agreguen al final de proyecto/Doxyfile:

Doxyfile · agregar al final
PROJECT_NUMBER         = $(APP_VERSION)
PROJECT_BRIEF          = "API de gestión de alumnos - OCY1102"

INPUT                  = app.py
FILE_PATTERNS          = *.py
OPTIMIZE_OUTPUT_JAVA   = YES

QUIET                  = YES
WARN_IF_UNDOCUMENTED   = YES
WARN_NO_PARAMDOC       = YES
WARN_LOGFILE           = reports/doxygen_warnings.log
  • PROJECT_NUMBER = $(APP_VERSION): toma la versión que define el pipeline (1.0.N+commit), así cada documento queda etiquetado con su build y su commit.
  • INPUT, FILE_PATTERNS: documentan solo app.py (sin tests ni scripts).
  • WARN_…: avisan de lo que falta documentar y guardan las advertencias en un archivo que el pipeline revisa.

Generen la documentación en el taller y lean las advertencias:

Terminal · carpeta jenkins/
docker compose exec taller bash -c "mkdir -p reports && APP_VERSION=local doxygen Doxyfile"
docker compose exec taller cat reports/doxygen_warnings.log

Abran proyecto/docs/html/index.html en el navegador: verán el encabezado con la versión local.

Checkpoint

El log muestra unas 9 advertencias (funciones y variables sin documentar). Si el número difiere un poco, está bien: lean qué dice cada una.

B2 · 20 min

Documenten el código hasta llegar a 0 advertencias

Doxygen no entiende la docstring actual de hello() («Parámetros: … Retorna: …»): necesita su propia sintaxis.

  • Funciones: docstring que empieza con """! y usa @brief, @param y @return.
  • Variables de módulo: un comentario ## en la línea anterior.
  • El módulo ya está documentado al inicio de app.py (mírenlo): si no lo estuviera, Doxygen no avisaría de nada y la documentación saldría vacía.
Ejemplo · app.py
## Aplicación Flask principal.
app = Flask(__name__)

@app.route('/alumnos/<int:alumno_id>')
def obtener_alumno(alumno_id):
    """!
    @brief Obtiene un alumno por su identificador.

    @param alumno_id Identificador numérico del alumno.
    @return JSON con el alumno, o error 404 si no existe.
    """
    ...

Su tarea:

  1. Documenten todas las funciones y variables de app.py y repitan los dos comandos de B1 hasta que el log quede vacío.
  2. Reescriban la docstring de hello() en formato Doxygen. name no es un parámetro de la función (viene de la URL): descríbanlo en el texto; si escriben @param name, Doxygen avisará.
  3. Ejecuten pytest otra vez: documentar no debe romper nada.
Me queda una advertencia sobre la variable debug. ¿Por qué?

Doxygen interpreta debug=… dentro de app.run(...) como una variable de módulo, porque la llamada está suelta al final del archivo. Si la llamada vive dentro de una función documentada (por ejemplo main()), el problema desaparece. Dejen if __name__ == '__main__': main() al final.

Cuando terminen, borren la carpeta generada: la versionará Jenkins en B4 y, si queda aquí, más adelante git pull se quejará.

Terminal · carpeta jenkins/
docker compose exec taller rm -rf docs
Evidencia E6

Captura de la página de Doxygen (con la función documentada) y del log de advertencias vacío. Háganla antes de borrar docs/.

Checkpoint

reports/doxygen_warnings.log está vacío y el HTML lista todas las funciones con su descripción.

B3 · 15 min

Etapa «Generate Documentation» en el pipeline

Reemplacen la línea >>> [B-DOCS] del Jenkinsfile por:

Jenkinsfile · reemplaza la línea [B-DOCS]
        stage('Generate Documentation') {
            steps {
                catchError(buildResult: 'UNSTABLE', stageResult: 'UNSTABLE') {
                    sh '''#!/bin/bash
                        set -eu
                        mkdir -p reports
                        rm -rf docs/html reports/doxygen_warnings.log
                        doxygen Doxyfile
                        if [ -s reports/doxygen_warnings.log ]; then
                            echo "Doxygen encontró código sin documentar o mal documentado:"
                            cat reports/doxygen_warnings.log
                            exit 1
                        fi
                        echo "Documentación generada sin advertencias en docs/html"
                    '''
                }
            }
            post {
                always {
                    archiveArtifacts artifacts: 'docs/html/**', allowEmptyArchive: true
                }
            }
        }

Si Doxygen emite advertencias, el build queda INESTABLE: es el control de calidad de la documentación.

Terminal · carpeta proyecto/
git add -A
git commit -m "Parte B: Doxygen y etapa Generate Documentation"
git push

Pulsen Build Now. Resultado esperado: SUCCESS. Si queda INESTABLE, abran el log de la etapa: Doxygen indica qué falta documentar.

Checkpoint

Build SUCCESS con la etapa Generate Documentation en verde y el log «Documentación generada sin advertencias».

B4 · 20 min

«Version Control»: versionar la documentación

Para que Jenkins pueda escribir en GitHub necesita una credencial. Se aplica el principio de mínimo privilegio: un token solo para este repositorio.

4.1 Creen el token

  1. GitHub → foto de perfil → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  2. Expiration: 7 días. Repository access: Only select repositories → sistema-alumnos.
  3. Repository permissions → Contents: Read and write (nada más).
  4. Generen el token y cópienlo en ese momento (GitHub no lo vuelve a mostrar).

4.2 Guárdenlo en Jenkins

Manage Jenkins → Credentials → Global credentials → Add Credentials: Kind Username with password · Username: su usuario de GitHub · Password: el token · ID: github-token (exacto) → Create.

Nunca peguen el token en el Jenkinsfile, en un script, en el informe ni en una captura. Si se filtra, revóquenlo en GitHub de inmediato.

4.3 Agreguen la etapa

Reemplacen la línea >>> [B-VERSION]:

Jenkinsfile · reemplaza la línea [B-VERSION]
        stage('Version Control') {
            // Solo se versiona la documentación de builds 100% correctos y NO en las ejecuciones programadas
            when {
                allOf {
                    expression { currentBuild.currentResult == 'SUCCESS' }
                    not { triggeredBy 'TimerTrigger' }
                }
            }
            steps {
                sh 'bash scripts/trazabilidad.sh'
                withCredentials([usernamePassword(credentialsId: 'github-token',
                                                  usernameVariable: 'GIT_USER',
                                                  passwordVariable: 'GIT_TOKEN')]) {
                    sh '''#!/bin/bash
                        set -eu
                        git config user.name  "Jenkins CI"
                        git config user.email "jenkins@localhost"
                        git add docs
                        if git diff --cached --quiet; then
                            echo "No hay cambios en docs/: nada que versionar"
                            exit 0
                        fi
                        # [skip ci] evita que este commit dispare otro build si algún día se activa un webhook
                        git commit -q -m "docs: documentación del build #${BUILD_NUMBER} (${APP_VERSION}) [skip ci]"
                        git tag -a "build-${BUILD_NUMBER}-${GIT_SHA}" -m "Build ${BUILD_NUMBER} - versión ${APP_VERSION}"

                        # Credenciales vía GIT_ASKPASS: el token no queda en la URL, ni en .git/config, ni en el log
                        ASKPASS="$(mktemp)"
                        trap 'rm -f "$ASKPASS"' EXIT
                        printf '#!/bin/sh\ncase "$1" in Username*) echo "$GIT_USER" ;; *) echo "$GIT_TOKEN" ;; esac\n' > "$ASKPASS"
                        chmod 700 "$ASKPASS"
                        GIT_ASKPASS="$ASKPASS" GIT_TERMINAL_PROMPT=0 git push origin HEAD:main --follow-tags
                    '''
                }
            }
        }

Esta etapa solo corre en builds 100 % correctos. Agrega una fila a docs/TRAZABILIDAD.md (scripts/trazabilidad.sh), deja un commit con [skip ci] y una etiqueta build-N-commit, y entrega el token a Git con GIT_ASKPASS para que no quede en la URL ni en el log.

B5 · 10 min

«Deploy» en el entorno de prueba

Reemplacen la línea >>> [B-DEPLOY]:

Jenkinsfile · reemplaza la línea [B-DEPLOY]
        stage('Deploy') {
            when { expression { currentBuild.currentResult == 'SUCCESS' } }
            steps {
                // Despliega en el "entorno de prueba" (http://localhost:5000) y ejecuta una prueba de humo
                sh 'bash scripts/deploy_test.sh'
            }
        }

Antes de ejecutar, lean scripts/deploy_test.sh: detiene la versión anterior, copia la aplicación, instala solo las dependencias de ejecución, la arranca con APP_VERSION y hace una prueba de humo (/health, /alumnos y que /version coincida con el build).

Terminal · carpeta proyecto/
git add -A
git commit -m "Parte B: etapa Deploy"
git push

Pulsen Build Now. Al terminar, abran en el navegador:

  • http://localhost:5000/version → debe mostrar la versión del build que acaba de terminar.
  • http://localhost:5000/alumnos → la lista de alumnos.
Evidencia E8

Pipeline completo en verde (las 5 etapas: Build, Test, Generate Documentation, Version Control y Deploy) y el navegador mostrando /version de la app desplegada.

Checkpoint

Pipeline completo en SUCCESS y localhost:5000/version coincide con el build.

B6 · 10 min

Recorran la cadena de trazabilidad

La trazabilidad responde: «Esto que está corriendo, ¿de qué código salió, quién lo construyó y dónde está su documentación?». Partan de lo único que ven en producción:

Terminal
curl http://localhost:5000/version

(Si no tienen curl, abran la dirección en el navegador.) La respuesta es algo como {"version": "1.0.N+abc1234", …}.

PreguntaCómo la responden
1. ¿Qué build de Jenkins lo generó?El número N de la versión → http://localhost:8080/job/sistema-alumnos/N/
2. ¿Con qué código?git show abc1234 (el commit después del +)
3. ¿Qué etiqueta lo marca?git tag --list "build-N-*"
4. ¿Dónde está su documentación?docs/html/index.html (la versión aparece en el encabezado) y la fila N de docs/TRAZABILIDAD.md
5. ¿Estaba sano ese build?Columnas Pruebas y Advertencias Doxygen de esa fila (la de pip-audit dice n/a si no hicieron la otra guía)
Para el informe

Escriban esa cadena con los valores reales de su último build (número, commit, etiqueta) y expliquen en una frase por qué la versión incluye el commit corto.

Fin de la guía.

Tienen un pipeline de cinco etapas con documentación completa, versionada en Git y un despliegue trazable hasta su commit.

Cierre

Entrega · 35 min

Qué entregar

Entreguen capturas del pipeline, los archivos de configuración y un informe con el proceso, las pruebas, los resultados y las mejoras propuestas. El formato y el medio de entrega los indica su docente.

Al terminar, limpien

Terminal · carpeta jenkins/
docker compose down        # apaga los contenedores y conserva los datos de Jenkins
docker compose down -v     # además BORRA los datos de Jenkins (incluidas credenciales)

Revoquen el token en GitHub (Settings → Developer settings → Fine-grained tokens) y, si usaron un equipo compartido, borren la carpeta del proyecto.

Si algo falla

Lean siempre el Console Output de abajo hacia arriba. Si se traban más de 10 minutos, miren esta lista y después consulten a su docente.

El puerto 8080 o 5000 ya está ocupado

En jenkins/docker-compose.yml cambien el número de la izquierda (por ejemplo "127.0.0.1:8081:8080"), ejecuten docker compose up -d y usen el puerto nuevo.

«the input device is not a TTY» (Git Bash en Windows)

Agreguen -T: docker compose exec -T taller …, o usen PowerShell.

El build falla en pipenv install --deploy («Pipfile.lock is out of date»)

Editaron el Pipfile sin regenerar el lock. Ejecuten docker compose exec taller pipenv lock, hagan commit de Pipfile.lock y suban.

git push es rechazado («non-fast-forward» / «fetch first»)

Jenkins subió un commit mientras editaban. Ejecuten git pull --rebase y repitan git push.

git pull dice que archivos de docs/ serían sobrescritos

Generaron docs/ localmente y Jenkins subió la suya. Borren la local (docker compose exec taller rm -rf docs) y repitan git pull.

«Could not find credentials entry with ID 'github-token'» o «Authentication failed»

El ID debe ser exactamente github-token. Revisen que el usuario sea el suyo de GitHub, que el token no haya expirado y que tenga Contents: Read and write sobre ese repositorio.

La etapa Deploy falla («Address already in use» o la app no responde)

Queda un proceso de un despliegue anterior. Ejecuten docker compose restart jenkins y repitan el build. El detalle está en docker compose exec jenkins cat /var/jenkins_home/entorno-prueba/app.log.

Doxygen: errores de @param, de etiquetas o documentación vacía
  • «argument 'name' of command @param is not found»: documentaron un parámetro que la función no recibe. Descríbanlo en el texto, sin @param.
  • «Unsupported xml/html tag <…> found»: escribieron algo entre < y > en una docstring. Escríbanlo sin esos signos (por ejemplo 1.0.N+commit).
  • Documentación vacía y sin advertencias: falta la cabecera """! con @file al inicio de app.py, o una docstring empieza con """ en vez de """!.
La documentación vista desde «Build Artifacts» no tiene estilos

Es normal: Jenkins bloquea scripts y estilos de los artefactos por seguridad. Ábranla desde el repositorio (después de B4).
